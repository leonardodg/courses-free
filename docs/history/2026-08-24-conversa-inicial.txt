Resposta direta primeiro

Para o seu cenário (VPS Oracle único, Docker, reverse proxy seu cuidando dos domínios), a resposta é IOMAD. Não é só "porque é grátis" — a arquitetura de container único do IOMAD bate exatamente com o jeito que reverse proxy + Docker funcionam. Deixa eu detalhar o porquê.

Como cada solução guarda os dados
	Modelo de dados
IOMAD	É uma "distro" do Moodle (core levemente alterado + plugins), não um plugin puro. Adiciona tabelas próprias — mdl_company, mdl_company_users, mdl_department, mdl_companytheme, mdl_iomad_courses, entre outras — que referenciam os IDs padrão do Moodle (userid, courseid). O isolamento entre empresas é aplicado no código do IOMAD (as queries filtram por companyid), não é uma trava estrutural do banco.
Moodle Workplace (tool_tenant)	A tenancy é nativa do core: o campo tenantid é adicionado diretamente nas tabelas centrais (usuários, categorias de curso, etc). O isolamento é imposto num nível mais baixo — qualquer ferramenta "tenant-aware" da Workplace já respeita isso automaticamente.
MuTMS (tool_mutenancy)	Também exige um patch no core (não é plugin puro), com uma abordagem parecida com a da Workplace, mas os próprios mantenedores dizem que não vão implementar domínio próprio por tenant — Moodle "não foi desenhado pra isso", segundo eles mesmos. Isso já elimina essa opção pro seu caso.

Como isso cai no seu Docker + reverse proxy

O ponto central, independente de IOMAD ou Workplace: é um único container Moodle rodando — não um container por professor. Seu reverse proxy não precisa saber nada sobre "empresa", ele só faz duas coisas:

Resolve DNS wildcard (*.suaplataforma.com) + os domínios próprios dos professores (meuscursos.joao.com), todos apontando pro IP do seu VPS.
Termina TLS e encaminha a requisição pro container Moodle, preservando o header Host.

Dentro do Moodle, o IOMAD lê esse Host e decide qual empresa/tema mostrar — isso é configurado por empresa na tela de edição da empresa (campo de URL customizada), não no proxy. Resultado: 1 VPS, 1 container Moodle, 1 banco, N domínios roteados só pelo cabeçalho Host. É leve, barato, e é literalmente o que proxies como Traefik/nginx-proxy/Nginx Proxy Manager já fazem bem (mapear host → upstream), sem duplicar a aplicação.

Compare com a alternativa "um Moodle inteiro por professor": mais isolado, mas cada professor vira container + banco próprio, multiplicando custo de VPS e manutenção. Nenhuma das três opções trabalha assim — todas assumem uma instalação compartilhada.

Onde entra o Mercado Pago nisso

O bloco de ecommerce do IOMAD já lida com conta de pagamento por tenant e "qualquer gateway suportado pelo Moodle" — vale investigar se dá pra plugar um gateway Mercado Pago ali em vez de escrever o local_mpsplit 100% do zero. Mas a lógica de split (marketplace_fee/application_fee, OAuth por vendedor) é uma feature específica do Mercado Pago que dificilmente um plugin genérico de gateway Moodle já resolve pronta — isso continua sendo trabalho customizado, independente de você escolher IOMAD ou Workplace.

Boa pergunta — isso esclarece uma imprecisão que deixei passar na resposta anterior. Depende de qual caminho você seguir:

Se você clonar o repo completo iomad/iomad (o que recomendei) — já vem tudo pronto. Esse repo é a distro inteira: blocks/iomad_company_admin, blocks/iomad_commerce, local/iomad, auth/iomadoidc etc. já estão dentro da árvore de pastas, no lugar certo. Você clona, configura o config.php, roda o instalador do Moodle e os blocos já aparecem disponíveis pra ativar — não precisa buscar nada separado.

Os repositórios separados que te mostrei (iomad/moodle-block_iomad_company_admin, iomad/moodle-block_iomad_commerce, etc.) existem pra um segundo caminho: quem já tem um Moodle vanilla rodando e quer adicionar IOMAD nele sem trocar de fork. Nesse caso sim, você:

Aplica o patch de core de iomad/moodle-core_patch no seu Moodle existente;
Baixa cada plugin individualmente e coloca na pasta certa (blocks/iomad_company_admin, blocks/iomad_commerce, local/iomad...);
Roda a atualização do Moodle pra instalar tudo.

Pro seu caso — começando do zero, com worktree novo — não faz sentido usar esse segundo caminho. Clone o iomad/iomad direto e pronto, os blocos já estão lá.
